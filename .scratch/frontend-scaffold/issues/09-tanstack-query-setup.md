## Question

Where does the TanStack Query `QueryClientProvider` live, and what is the usage pattern that respects the BFF constraint?

Since the BFF pattern means all FastAPI calls are server-side, TanStack Query cannot be used in the usual way (direct API calls from the browser). Its role in this app is narrower:

Decisions to lock:
- `QueryClientProvider` placement: does it wrap the entire `(authenticated)` group layout, or just the specific pages/components that need it (chat, dashboard polling)?
- Pattern for initial data: Server Components fetch + pass as `initialData` to TanStack Query on the client? Or use `prefetchQuery` + dehydrate/hydrate pattern?
- Which specific features actually need TanStack Query in the MVP? (Chat streaming state, task polling, optimistic task status update?)
- Is there a risk of leaking the FastAPI client into client-side code via TanStack Query `queryFn`? What is the guardrail?

## Decision (2026-10-14, trellis/12 D50)

TanStack Query is used **only for optimistic updates** on pages that are already built. Reads and writes keep their existing paths.

- **Initial data:** the page's Server Component still loads the data (`lib/api/queries/`) and passes it to the client component, which seeds the query cache with it. The rule is **"the server's fresh copy wins"**: whenever the server sends new page data (after a Server Action's `revalidatePath` / `refresh()`, or on returning to the page), it replaces the cached copy. Nothing re-reads from the browser, so there are no read endpoints, and Route Handlers stay for streaming only (D18).
- **Writes:** `useMutation` calls the existing Server Action. `mutationFn` throws on `{ ok: false }`. `onMutate` takes a snapshot and applies the change; a create gets a temporary uuid and shows as pending (buttons disabled). `onSuccess` swaps in the real id from the reply. `onError` restores the snapshot and shows a toast.
- **Which features:** Admin Members, Admin Documents (edit and delete; the existing "Indexing…" check is unchanged), the Chat sidebar list (new, rename, delete; the message stream keeps `use-chat-stream`), then Admin Roles. Dashboard and Teams are skipped for now.
- **Guardrail:** no `queryFn` ever imports the `api` client. Client code only calls Server Actions (`'use server'`) and receives server data as props, and `lib/api/client.ts` keeps its `import 'server-only'`.
- **Provider placement and file locations (Piyush, 2026-10-14):** everything lives in `lib/query/`: `provider.tsx` (`QueryProvider`, `staleTime: Infinity`, so nothing refetches by itself), `use-server-data.ts` (`useServerData`; the cache is replaced only when the server's copy has different content, so a pending instant change isn't undone by an identical copy) and `action.ts` (`fromAction`). `QueryProvider` wraps the signed-in app in `app/(dashboard)/layout.tsx`, keyed by `active_org.org_id`, so switching org starts a fresh cache (D12: each org's data stays separate).
- **Built 2026-10-14:** `@tanstack/react-query` 5.104 added. `tsc`, eslint on the changed files and `next build` pass. Nothing on screen changes until a page uses it.
- **Page 1, Admin → Members, built 2026-10-14:** `members/_components/use-member-changes.ts` holds the page's four instant changes (remove, change role, cancel invite, invite). It is the example for the other pages. The dialogs call it and close at once. Invite adds a greyed "Sending…" row with a temporary id and its Cancel button disabled; on success that row becomes the real invite, or the person moves to Members if they already use Trellis. `fromAction` also turns "no answer at all" (offline, server down) into a plain toast. `tsc`, eslint and `next build` pass. Not yet tried in a browser.
- **Fix 2026-10-14:** `QueryProvider` sets `mutations: { networkMode: "always" }`. TanStack's default holds a change while the browser reports it's offline and sends it once it's back online. A Remove tried on DevTools "Offline" would therefore still run later instead of rolling back. This was shown in a standalone test app (Next 16.3.3 + TanStack 5.104.2). The same test app showed the optimistic pattern itself works: the row is gone within ~50 ms while a 3 s Server Action runs, also inside the shadcn Dialog, for create-then-cancel, and for cancelling the only row. **Checked in Piyush's browser 2026-10-14:** instant Cancel invite works after restarting the app (the first try was running the old build).
- **Page 2, Admin → Documents, built 2026-10-14:** `documents/_components/use-document-changes.ts` makes Delete and Edit (title, description, audience) instant. Upload's step 1 (the file going to UploadThing) is unchanged. **Amended the same day (Piyush): step 2's Save is instant too.** The dialog closes and a greyed "Saving…" row appears with a temporary id, with no Edit or Delete and left out of the indexing check. On success it becomes the real "Indexing…" row. Trade-off accepted: a rare refusal means uploading the file again. The "Indexing…" check (`checkProcessingDocuments` + `refresh()`) is unchanged; its fresh copy replaces the cache through `useServerData`. `tsc`, eslint and `next build` pass. Piyush confirmed Edit, Delete and the instant Save in the browser.
- **Page 3, Chat sidebar, built 2026-10-14:** `chat/_components/use-chat-changes.ts` makes Rename and Delete instant. Deleting the open chat goes to `/chat` at once, before the delete is sent. When a new chat's first message is sent, a greyed "New chat" row (temporary id, no link or menu) shows at the top. `ChatConversation` calls `create.mutateAsync()` so it gets the real id before streaming. A failed create removes the row with a toast and doesn't send. Streaming, and the title and order refresh after an answer, are unchanged. `tsc`, eslint and `next build` pass. **Fixed after Piyush's test:** your first message in a new chat also shows at once. Piyush confirmed it in the browser.
